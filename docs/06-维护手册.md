## 1. 已知限制

| 编号 | 限制 | 影响与说明 |
| --- | --- | --- |
| L1 | 仅支持 MD5、SHA-256 两种算法 | SHA-1、SHA-512、SM3 等留作扩展点，见第 2 节 |
| L2 | 目录扫描采用递归实现 | 目录层级极深（数万层）时理论上可能栈溢出；常规文件系统深度下无影响，可按第 2.2 节改为迭代式 |
| L3 | 无定时巡检/基线库/告警 | 本期为“按需手动校验 + 报告导出”，不做自动基线管理 |
| L4 | 纯本地、无网络能力 | 不支持远程扫描与云端比对（设计如此，见非目标） |
| L5 | GUI 交互以人工验收为准 | 未引入第三方 UI 自动化库；界面逻辑通过 EDT 走查 + 启动冒烟 + 业务层自动化间接保证 |
| L6 | Windows 无权限场景难自动化 | `FileScaner` 对 `listFiles()` 返回 null 已做空值保护；该分支以代码走查确认 |
| L7 | 不制作 exe/msi 安装包 | 交付可执行 jar + 启动脚本（绿色软件） |

## 2. 扩展指南

### 2.1 新增哈希算法（例如 SHA-512 / SM3）

改动点小且集中，无需修改业务层并发与界面框架：

1. **算法来源**：JDK 内置算法（如 `SHA-512`）无需任何新依赖，直接在
   `HashCheckGUI` 的算法常量数组中追加名称即可：
   ```java
   private static final String[] ALGORITHMS = {"MD5", "SHA-256", "SHA-512"};
   ```
   `HashUtil.getFileHash` 通过 `MessageDigest.getInstance(algorithm)` 动态获取，天然支持；
2. **JDK 不内置的算法（如 SM3）**：在 `HashUtil` 内部以面向接口方式隔离第三方提供者
   （引入 BouncyCastle 等），保持 `getFileHash(File, String)` 签名不变，则服务层、
   GUI、报告导出均无需改动；
3. **测试**：在 `HashUtilTest` 增加新算法的标准测试向量（空文件 + 已知内容）
   与长度/正则断言；在下拉框相关人工验收中补充一项；
4. **文档**：同步更新《需求规格说明书》非目标条目与本手册限制 L1。

### 2.2 以迭代遍历替代递归（超深/超大目录）

将 `FileScaner.scanDirectory` 的递归改写为基于 `Deque<File>` 的深度优先迭代：

```java
Deque<File> stack = new ArrayDeque<>();
stack.push(root);
while (!stack.isEmpty()) {
    File current = stack.pop();
    File[] children = current.listFiles();
    if (children == null) { continue; } // 保持无权限跳过策略
    for (File child : children) {
        if (child.isFile()) { result.add(child); }
        else if (child.isDirectory()) { stack.push(child); }
    }
}
```

对外签名 `scanFiles(File)` 与返回契约保持不变，现有测试应全部继续通过。

### 2.3 超大目录策略建议

- 结果改为分块渲染（每 100 条 `invokeLater` 一次），避免文本区频繁重排；
- 报告写出已为流式（逐行 write），天然支持大量记录；
- 如未来需要取消功能，可在 `HashCheckService.checkAll` 传入 `AtomicBoolean cancelled`，
  任务执行前检查并以“已取消”失败结果收尾，`shutdownNow()` 中断在途任务。

### 2.4 新增“与基线比对”功能的建议位置

- 新增 `service.BaselineService`（加载/保存历史报告或 properties 基线），
  不要把比对逻辑放进 GUI；
- `FileHashResult` 可新增枚举字段或复用 `errorMessage` 表达“与基线不一致”；
- 报告导出在 `ReportWriter` 增加重载，保持老签名兼容。

## 3. 缺陷反馈与处理流程

1. **记录**：记录操作系统、JDK 版本（`java -version`）、复现步骤、目标类型
   （单文件/目录）、算法名、界面状态栏文案与 stderr 输出；
2. **复现与定位**：
   - 哈希值问题 → 先用 `HashUtilTest` 的标准向量判断是否环境问题；
   - 批量问题 → 缩小到单文件调用 `HashUtil.getFileHash` 定位是 IO/权限还是调度问题；
   - 界面问题 → 确认是否在 EDT 更新组件（搜索 `SwingUtilities.invokeLater`）；
3. **修复要求**：
   - 缺陷修复必须先在对应测试类新增一个**会失败的回归用例**，再修改源码使其通过；
   - 执行 `mvn clean test` 确认 40+ 用例全绿、覆盖率不下降；
4. **发布**：按第 4 节版本规范在 `fix/...` 分支修复、合并到主干并打补丁版本标签。

## 4. 版本记录与版本控制规范

### 4.1 语义化版本（SemVer）

版本号格式 `主版本号.次版本号.修订号`（`MAJOR.MINOR.PATCH`）：

- **PATCH（1.0.x）**：向后兼容的缺陷修复；
- **MINOR（1.x.0）**：向后兼容的功能新增（如新增 SHA-512 算法、取消功能）；
- **MAJOR（x.0.0）**：不兼容的接口/报告格式变更。

当前版本：**v1.0.0**（首次课程交付）。版本号在 `pom.xml` 的 `<version>` 与
窗口标题中保持一致；每次发布在 Git 上打带注释标签：`git tag -a v1.0.0 -m "..."`。

### 4.2 Git 分支模型

| 分支 | 用途与规则 |
| --- | --- |
| `main` | 主干，**任何时刻均可构建发布**；只接受合并，不直接推送零散提交 |
| `feature/<名称>` | 新功能开发分支，从 main 切出，完成后合并回 main |
| `fix/<名称>` | 缺陷修复分支，流程同 feature |
| `docs/<名称>` | 纯文档修订分支（可选，小改可直接合入） |

合并方式：功能/修复分支以 `--no-ff` 合并到 main，保留可识别的分支历史；
合并前必须通过 `mvn clean test`。

### 4.3 提交信息规范（Conventional Commits）

格式：`<类型>: <中文简述>`，正文按需补充动机与要点。类型限定：

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `test` | 测试新增/修改 |
| `docs` | 文档 |
| `refactor` | 不改变行为的重构 |
| `chore` | 构建、脚本、工程配置 |

示例：`feat: 新增 HashCheckService 固定线程池并发批量校验`。
`target/` 等构建产物通过 `.gitignore` 排除，不入库。

### 4.4 v1.0.0 交付时的版本库实践

- 初始功能在 `feature/initial-implementation` 分支按“骨架 → 代码 → 测试 → 文档 → 脚本”
  分原子提交完成；
- 全量测试通过后以 `--no-ff` 合并到 `main`；
- 打带注释标签 `v1.0.0`；
- 推送到 GitHub 远程仓库对应分支与标签。

## 5. 维护检查清单

每次变更发布前逐项核对：

- [ ] `mvn clean test` 全绿，0 失败 0 错误（当前基线 40 个用例）；
- [ ] `mvn clean package` 成功，jar 清单 Main-Class 正确；
- [ ] JaCoCo 报告已重新生成，service/io/model 行覆盖不低于 80%；
- [ ] 新增/变更公共方法具备中文 Javadoc，签名与《详细设计说明书》一致或已同步修订文档；
- [ ] 变更涉及界面时，执行一次 GUI 启动冒烟（jar 或 bat），无异常堆栈；
- [ ] 无运行时第三方依赖被无意引入（`pom.xml` 依赖仍仅 JUnit 测试作用域）；
- [ ] 代码与文档仍为 UTF-8；新增文档放入 `docs/` 并使用中文；
- [ ] 提交信息符合第 4.3 节规范；在 feature/fix 分支开发，合并 main 后更新标签与版本号；
- [ ] `target/`、临时文件未被提交。
